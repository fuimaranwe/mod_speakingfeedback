# Browser acceptance checks

Run on a test course with one editing teacher, two students in separate groups, and an activity configured with a test Groq key. Use HTTPS or localhost. Run recording checks in Chrome, Edge, Firefox, and Safari (macOS/iOS); use real audio for final verification, not only browser fake-media flags.

1. Create/edit the activity; check description, instructions with an embedded image, timings, editable prompt, attempts, tags, restrictions, completion, and groups. Save without a replacement key and verify it remains configured without appearing in HTML or browser requests.
2. Deny microphone access: an actionable error appears and preparation does not start. Grant permission and retry.
3. Start a 5-second preparation / 10-second recording: no audio is captured during preparation; recording starts automatically and stops at the limit. With zero preparation it starts immediately. Stop early, listen, re-record, and verify the attempt count stays unchanged until submission.
4. Submit: inspect only same-origin requests from the browser. Check saving, transcribing, and feedback states; transcript and feedback appear. The microphone indicator goes off after stopping. Confirm completion occurs only after feedback succeeds.
5. With a one-attempt limit, double-click Get feedback and retry the upload request: only one accepted attempt and one recording exist. Open another tab and verify the server rejects an additional submission after the limit is reached.
6. Interrupt connectivity after upload and after transcription. Reload and retry from history; no new attempt is consumed, and an existing transcript is reused. With invalid keys, quota limits, and unavailable Groq, saved work remains and errors contain no provider payloads or credentials.
7. Disconnect the microphone during preparation/recording. No incomplete recording is offered as successful. Background the tab and return; the countdown follows elapsed time. Leaving with an unsubmitted recording triggers the browser's navigation warning.
8. Check history and teacher report with over 25 attempts. Search by student name and filter by group. Students cannot open another student's audio URL or manipulate another attempt ID. A teacher without access-all-groups cannot open recordings from another separate group.
9. Duplicate the activity: question, timing and prompt survive, but the new activity has no configured key. Back up and restore with user data; recordings and results survive without generating new API requests. Test without user data as well.
10. Export/delete a student's data through Moodle privacy tools. Confirm audio and attempt records are exported/deleted and unrelated students/credentials are unaffected. Test course reset and activity deletion.
11. Check Weeky and Boost at 320px, tablet, desktop and 200% zoom. Use keyboard only; verify visible focus, labelled audio controls, readable contrast, and restrained screen-reader announcements. Confirm transcripts and AI HTML cannot execute scripts.

12. As a teacher, open Student attempts and select Delete attempt. Cancel once and confirm the data remains; confirm deletion and verify the audio URL no longer serves the recording, the transcript/feedback disappear, and a limited student regains one attempt. Deleting the last feedback result recalculates automatic completion; deleting one of two completed attempts leaves completion satisfied. Manual completion stays unchanged. Students and teachers without the deletion capability see no delete action and cannot use the endpoint. Changing the activity or attempt ID must not bypass group restrictions. A GET URL with confirm=1 must only show confirmation; POST without a valid sesskey must fail. Try deletion during processing and verify the busy message leaves the attempt intact. Check Moodle logs for the deletion event.

Record browser versions and pass/fail results during deployment acceptance. A Windows-only environment cannot establish Safari microphone compatibility.
